# ApexNav Details

Source: Zhang et al., "ApexNav: An Adaptive Exploration Strategy for Zero-Shot Object Navigation with Target-centric Semantic Fusion," IEEE RA-L, 2025 (arXiv:2504.14478v3), Section IV (Methodology) and Section V-A (Implementation Details). Cross-referenced against the GitHub repo (`Robotics-STAR-Lab/ApexNav`) README and source (`vlm/detector/*`, `apexnav_environment.yaml`).

## Model Components

### Model Inventory

| Role | Model | Function in ApexNav | Paper Reference |
|---|---|---|---|
| VLM (frontier scoring) | **BLIP-2** | Generates the semantic score map: each RGB frame + a text prompt (e.g. "Seems there is a `<target_object>` or a `<target_room>` ahead") is scored via BLIP-2 image-text matching (cosine similarity), producing the 2D relevance map used to decide semantic- vs. geometry-based exploration mode. | Sec. IV-A2; Sec. V-A: "The semantic score map is generated by BLIP-2 [10]." |
| Object detector (COCO categories) | **YOLOv7** | Detects target/similar-object instances that fall within COCO's 80 categories, chosen for its strong performance on that category set. | Sec. IV-C2: "We use YOLOv7 [21] for objects within the COCO dataset due to its strong performance." |
| Object detector (open-vocabulary) | **GroundingDINO** | Detects everything outside COCO's category set — open-vocabulary detection driven by the text descriptions of the target and LLM-generated similar-object list. | Sec. IV-C2: "...and Grounding-DINO [13] for the rest." |
| Segmentation | **Mobile-SAM** | Segments each detected bounding box to produce a mask, from which the corresponding 3D point cloud is extracted from the depth map (DBSCAN removes noise). | Sec. IV-C2: "Detected object instances are segmented by Mobile-SAM [29] using their bounding boxes..." |
| LLM | **DeepSeek-V3** | Three offline/pre-episode roles: (1) generates the list of visually-similar objects that could be misclassified as the target (`L_obj`), via Chain-of-Thought prompting; (2) infers the most likely room type per target category (used to augment BLIP-2's text prompts); (3) generates an adaptive per-object detection confidence threshold `c_th`. | Sec. IV-C1 (roles); Sec. V-A: "DeepSeek-V3 [11] is used to generate the similar object list, rooms where objects are likely to appear, and detection confidence thresholds." |

### Non-obvious point: repo default diverges from the paper's LLM

The paper's reported SR/SPL numbers were generated using **DeepSeek-V3** for all three LLM roles above. However, the public GitHub repo does **not** call DeepSeek-V3 live by default — it ships the pre-generated LLM outputs directly in `llm/answers/`, so a normal run skips LLM inference entirely. The repo's *optional* live-LLM path (if you want to regenerate `llm/answers/` yourself, e.g. for a new target category not already covered) uses **ollama + `qwen3:8b`** instead, a small local open-weight model — not DeepSeek-V3, and not an API call.

This matters directly for the ablation plan (Initial Paper, Sec. II-C): swapping the LLM component means either (a) evaluating against the shipped `llm/answers/` outputs (effectively "DeepSeek-V3, frozen, as the paper used it") as one arm, or (b) standing up a live LLM call (qwen3:8b locally, or wiring in GPT-4o/LLaMA 3 as proposed) to regenerate `L_obj`, room inference, and `c_th` per model — these are two different things to hold constant vs. vary.

### Hardware baseline (context for benchmarking phase)

Paper's simulation results were produced on an **NVIDIA RTX 4090 + Intel i9-13900K (32 threads)** — worth keeping in mind when comparing reproduced timing/throughput on M3's T4/A40 nodes; SR/SPL should be hardware-invariant (deterministic given the same episodes/seeds), but wall-clock reproduction time won't be comparable.

### Relevance to shared model-weights storage

All four non-LLM models above (BLIP-2, YOLOv7, GroundingDINO, Mobile-SAM) are common building blocks across the broader ZSON literature surveyed in the Initial Paper (VLFM also uses BLIP-2; SG-Nav/UniGoal use similar detector stacks) — supporting the earlier decision to store their weights under a shared `/scratch2/$MPROJECT/$USER/data/model_weights/` location (symlinked into `ApexNav/data/`) rather than nested inside the ApexNav repo alone, in case UniGoal reuse becomes relevant later.

## Datasets Considered

ApexNav is evaluated on the ObjectNav task in the **Habitat** simulator [16], across three large-scale benchmarks, each originally introduced as a Habitat Challenge dataset. Each combines a **scene dataset** (the 3D building/room geometry, requiring separate license approval) with an **episode dataset** (start position + target object per episode, no license needed, distributed directly by Habitat/fbaipublicfiles).

| Dataset | Source | Scenes | Episodes (val) | Goal categories | Paper baseline (SR / SPL) |
|---|---|---|---|---|---|
| **HM3Dv1** | HM3D-Semantics-v0.1 [18], 2022 Habitat Challenge | 20 | 2000 | 6 | 59.6 / 33.0 |
| **HM3Dv2** | HM3D-Semantics-v0.2 [24], 2023 Habitat Challenge | 36 | 1000 | 6 | 76.2 / 38.0 |
| **MP3D** | Matterport3D [4], 2021 Habitat Challenge | 11 | 2195 | 21 | 39.2 / 17.8 |

Paper reference: Table I (SR/SPL baseline numbers); Datasets paragraph (scene/episode/category counts and challenge provenance, quoted directly): *"We evaluate methods in Habitat [16] simulator on three large-scale datasets: HM3Dv1 (HM3D-Semantics-v0.1 [18] from 2022 Habitat Challenge, 2000 episodes, 20 scenes, 6 goal categories), HM3Dv2 (HM3D-Semantics-v0.2 [24] from 2023 Habitat Challenge, 1000 episodes, 36 scenes, 6 goal categories), and MP3D (Matterport3D [4] from 2021 Habitat Challenge, 2195 episodes, 11 scenes, 21 goal categories)."*

Notes:
- HM3D scenes require Matterport license approval (API token); MP3D scenes require a separate Terms of Use application to the Matterport3D maintainers. Both are gating steps before any evaluation can run — see `ApexNav_M3_Setup.md` Step 1 for the full approval/download trail.
- The episode zips (`objectnav_hm3d_v1`, `objectnav_hm3d_v2`, `objectnav_mp3d_v1`) are separate downloads from the scene data itself and carry no license requirement.
- `habitat_evaluation.py --dataset {hm3dv1,hm3dv2,mp3d}` runs each dataset's full val split independently by default (no shared state or index dependency between datasets) — HM3Dv2 is the repo's own CLI default if `--dataset` is omitted.
- Full-sweep benchmark runs (all episodes, one dataset per `sbatch` submission) are the current in-progress task — see `jobs/run_benchmark.sh`.

### Evaluation protocol & result variance (confirmed from source, 2026-07-14)

Read `habitat_evaluation.py` directly to confirm two methodology points relevant to comparing reproduced results against Table I:

- **Single pass, not repeat-and-average.** The eval loop (`for epi in range(number_of_episodes - num_total):`) walks the episode set exactly once, advancing via `env.current_episode = next(env.episode_iterator)` and accumulating `spl_all`/`num_success`/etc. as running sums. The SR/SPL printed at the end is that cumulative total divided by episode count — there is no outer loop that repeats the full dataset multiple times and averages across runs. This applies per dataset (HM3Dv1, HM3Dv2, MP3D each get one pass), not once for all three combined.
- **No explicit seeding — the pipeline is a genuinely async, real-time system.** No `random.seed`/`np.random.seed`/`torch.manual_seed`/`env.seed` call anywhere in the script. Episode start conditions (agent pose, target) are fixed per `episode_id`, but the action-decision loop runs over live ROS pub/sub: observations are published on a timer, the script blocks on a subscriber callback (`/habitat/plan_action`) for the next action, and that action comes from a separate exploration-planner node reacting to detector/VLM output. Because GPU inference latency, thread scheduling, and ROS message delivery timing aren't deterministic between runs, the same `episode_id` can produce different trajectories run to run — confirmed empirically (Broden ran one episode 3x, got varying results).
- **Practical implication:** since the paper's own Table I numbers came from a single pass with the same non-deterministic pipeline, they carry the same unstated run-to-run noise, just diluted across ~1000-2195 episodes rather than concentrated in one. A few points of SR/SPL difference between a reproduced run and Table I may just be that inherent noise rather than a setup bug. Worth characterizing directly — e.g. rerunning a small subset (10-20 episodes) 3x each — before treating any single full sweep as "the" reproduced number.

## Failure-Mode Taxonomy & Result Format

### Where failure labels are recorded

Every episode's outcome — not just the aggregate SR/SPL — is written to disk twice per episode, via two `write_record()` calls in `habitat_evaluation.py`'s main loop:

- `record_file_path` (`record.txt`): paired with `table1`, the running **Average** metrics (Average Success/SPL/Soft SPL/Distance to Goal) as of that episode.
- `continue_path` (`continue.txt`): paired with `table2`, the running **Total** (cumulative) metrics — this is also what `read_record()` parses on job resume/restart.

Both files get an identical trailer per episode, written by the shared `write_record()` helper (`basic_utils/record_episode/write_record.py`):

```
Scene ID: <scene_id>
Episode ID: <per-scene episode_id>
<table>
success or not: <result_text>
target to find is <label>
No.<num_total> task is finished
<time_spend> seconds spend in this task
```

Records are **prepended**, not appended — the top of either file is always the most recent episode, the bottom is episode No.1 (job start). `Episode ID` is scene-relative (resets to 0 for every new scene the iterator moves to, since Habitat's episode datasets are stored per-scene) — it is NOT a unique or global identifier on its own. `No.<num_total>` is the only field that's a true global, monotonically-increasing count across the whole run.

### `result_text` categories (`check_failure()`, `basic_utils/failure_check/failure_check.py`)

When an episode isn't a clean `"success"`, `check_failure()` classifies it into one of the following (`params.py`'s `RESULT_TYPES`):

| Category | Meaning | Condition (from source) |
|---|---|---|
| `infeasible` | Target is on a different floor than the agent — genuinely unreachable given the episode's start position. | `is_on_same_floor()` fails for every goal. |
| `no frontier` | Agent ran out of explorable space with no detection at all. | Active stop, `final_state == NO_FRONTIER` (or `expl_result == SEARCH_EXTREME`), and the agent never got close enough to the true target (`pass_object == 0`). |
| `false positive` | Agent actively stopped believing it found the target, but was at the wrong location. | Active stop, `final_state == REACH_OBJECT`, but `near_object == 0`. |
| `stepout feasible` | Hit the max-step limit (passive stop) without ever passing near the target; target was reachable. | `step_out == True`, `near_object == 0`, `pass_object == 0`. |
| `stepout true negative` | Hit the max-step limit but happened to stop near the target without recognizing it. | Passive stop, `near_object == 1`. |
| `stucking` | Agent got stuck (planner-reported) before reaching or passing the target. | `final_state == STUCKING`, `pass_object == 0`. |
| `[no frontier] false negative` | Exploration exhausted, **but the agent's path did pass near the true target and still didn't stop for it** — a perception miss, not an exploration miss. | Same as `no frontier` but `pass_object == 1`. |
| `[stucking] false negative` | Got stuck, but had already passed near the target beforehand. | Same as `stucking` but `pass_object == 1`. |
| `[stepout] false negative` | Hit the step limit, had passed near the target earlier, but never stopped for it. | Same as `stepout feasible` but `pass_object == 1`. |

The three `[...] false negative` categories are the most diagnostically interesting: they isolate cases where the *navigation/exploration* succeeded (the agent's path genuinely brought it near the target) but the *detection/decision* stack failed to recognize and act on it — as opposed to every other failure category, where the agent never got close in the first place. Separating these out is what lets you report "X% of failures are navigation problems vs. Y% are perception problems," rather than a single flat failure rate.

### Re-running a specific logged episode (e.g. for video/qualitative review)

The full sweeps run with `need_video: false` (sane default — video for 2000 episodes would be enormous), so no footage exists for any already-completed episode. To generate one, re-run it individually:

```
python habitat_evaluation.py --dataset <dataset> test_epi_num=<N> need_video=true
```

**Important:** `test_epi_num` is a 0-indexed position in `env.episode_iterator`'s global traversal order — it is NOT the scene-relative `Episode ID` printed in the logs. The correct mapping is via `No.<num_total>`, since that field is exactly "how many episodes the iterator has produced so far, 1-indexed" — the same count the resume mechanism (`env_count = num_total`) relies on to skip forward correctly on restart. So:

```
test_epi_num = No.<num_total> - 1
```

E.g. a logged entry with `No.2194 task is finished` corresponds to `test_epi_num=2193`. `Scene ID`/`Episode ID` are useful for human identification (confirming you re-ran the right one — the re-run's printed Scene ID/Episode ID at the top should match), but they can't be used to *compute* the right index without also knowing the exact per-scene episode counts and scene ordering the iterator uses. This assumes the dataset/config/habitat-lab version are unchanged between the original run and the re-run — worth validating once (re-run a known `No.X`, confirm the printed Scene ID/Episode ID match the log exactly) before trusting it for new investigative re-runs.

Single-episode re-runs (`flag_once=True`) always save to `videos/video_once.mp4` regardless of pass/fail, overwriting on each subsequent run — rename it between runs if reviewing multiple specific episodes.
